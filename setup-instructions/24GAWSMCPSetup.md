# Set Up the AWS MCP Server for 24G Agents

Version: 0.1.0
Updated: 2026-09-21
Repository: <https://github.com/twentyfourg/24g-aws-sso>

You MUST report the version above to the user at the start of a run. Bump the
patch number for wording or troubleshooting changes and the minor number when a
command or step changes.

## Overview

This setup file configures local AI coding agents to use the AWS MCP Server
through the MCP Proxy for AWS and an explicit allowlist of 24G AWS IAM Identity
Center profiles.

The workflow:

- Ensures the machine has working 24G Identity Center profiles
- Lets the user choose exactly which profiles the agent may use
- Uses a read-only or least-privileged profile as the default when available
- Runs `aws configure agent-toolkit` to install optional AWS skills and create
  the base MCP configuration for detected agents
- Adds the multi-profile allowlist to every generated `aws-mcp` entry
- Preserves unrelated MCP servers and settings
- Verifies the AWS CLI profiles and each agent configuration

This file is re-runnable. It MUST inspect the current state and ask before
changing an existing `aws-mcp` entry.

## Why a post-configuration edit is required

`aws configure agent-toolkit` accepts the normal AWS CLI `--profile` global
option, but that option selects credentials for the setup command itself. It
does not write a profile allowlist into the generated MCP server entry.

The MCP Proxy for AWS supports multiple profiles in either of these equivalent
ways:

```bash
mcp-proxy-for-aws https://aws-mcp.us-east-1.api.aws/mcp \
  --profile readonly-24g app-24g production-24g
```

```bash
AWS_MCP_PROXY_PROFILES="readonly-24g app-24g production-24g" \
  mcp-proxy-for-aws https://aws-mcp.us-east-1.api.aws/mcp
```

This workflow uses `AWS_MCP_PROXY_PROFILES` in the MCP server's `env` block.
That keeps the Agent Toolkit-generated command and arguments intact and works
with JSON clients and Codex's TOML configuration. The environment variable
takes precedence over `--profile` and `AWS_PROFILE`.

The first listed profile is the default. Only listed profiles are available to
the agent. The proxy adds an `aws_profile` parameter to authenticated AWS MCP
tools so the agent can select another allowed profile for an individual call.

## Security rules

- Treat the profile list as an allowlist, not as a discovery convenience.
- MUST NOT automatically expose every profile returned by
  `aws configure list-profiles`.
- MUST ask the user which profiles may be used through MCP.
- SHOULD put a read-only or otherwise least-privileged profile first.
- MUST verify that every requested profile exists locally.
- MUST NOT ask for access keys, secret keys, SSO access tokens, or passwords.
- MUST NOT read or modify `~/.aws/credentials`.
- MUST NOT print complete agent configuration files. They may contain tokens
  for unrelated MCP servers. Inspect and edit only the `aws-mcp` entry.
- MUST preserve all unrelated MCP servers, settings, comments, and formatting
  to the extent supported by the file format.
- MUST create a rollback copy before the first write.
- MUST NOT put an AWS account ID, role ARN, access token, or credential in the
  MCP configuration. Profile names are sufficient.
- SHOULD use client-side approval rules or hooks for production profiles when
  the selected agent supports them. The profile allowlist controls identity
  selection; it does not add a human approval gate.

## Known user-level configuration locations

Use the paths printed by `aws configure agent-toolkit` as the source of truth.
Common defaults are:

- Cursor: `~/.cursor/mcp.json`
- Claude Code: `~/.claude.json`, top-level `mcpServers`
- Gemini CLI: `~/.gemini/settings.json`
- Kiro: `~/.kiro/settings/mcp.json`
- Codex CLI and desktop: `~/.codex/config.toml`

On Windows, `~` means `%USERPROFILE%`. Project-level MCP files may also exist,
but this workflow configures the user-level files written by the Agent Toolkit
unless the user explicitly requests project scope.

If `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or another agent-specific configuration
override is set, use that client's reported path instead of the default.

## Step 0: Inspect the current state

Run read-only checks:

```bash
aws --version
uvx --version
aws configure list-profiles
```

Requirements:

- AWS CLI 2.35.0 or later for `aws configure agent-toolkit`
- `uvx`
- At least one approved named AWS profile
- MCP Proxy for AWS 1.6.0 or later for multi-profile switching

Check which known agent configuration files exist, but do not print them:

```bash
for file in \
  "$HOME/.cursor/mcp.json" \
  "$HOME/.claude.json" \
  "$HOME/.gemini/settings.json" \
  "$HOME/.kiro/settings/mcp.json" \
  "$HOME/.codex/config.toml"
do
  [ -f "$file" ] && printf 'found: %s\n' "$file"
done
```

For JSON files, test for an existing user-level entry without printing it:

```bash
jq -e '.mcpServers["aws-mcp"]' <path> >/dev/null 2>&1
```

For Codex, search only for the table header:

```bash
grep -q '^\[mcp_servers\.aws-mcp\]$' "$HOME/.codex/config.toml"
```

Report what is installed, which agents were detected, which requested profiles
exist, and which files already have `aws-mcp`. Ask for the decisions listed
above before making changes.

**Success:** The target agents, ordered profile allowlist, skill choice, and
existing-entry behavior are known.

## Step 1: Ensure 24G Identity Center profiles exist

If the requested profiles do not exist, follow the sibling
[`24GAWSSOSetup.md`](24GAWSSOSetup.md) workflow first. When this file is being
run from a raw URL, retrieve:

<https://raw.githubusercontent.com/twentyfourg/24g-aws-sso/main/setup-instructions/24GAWSSOSetup.md>

That workflow configures the `24g` SSO session and creates one named profile
per selected account and role. Resume here after its verification step.

If the profiles already exist but the SSO session is expired, use the existing
Identity Center flow:

```bash
aws sso login --sso-session 24g
```

The browser interaction belongs to the human user. Wait for it to complete.
Do not replace this established Identity Center workflow with `aws login`.

Verify every approved profile, one at a time:

```bash
aws sts get-caller-identity --profile <profile>
```

Confirm that the returned account and role match the profile's intended
identity. Do not continue with a profile that fails verification.

**Success:** Every profile in the approved allowlist exists and
`get-caller-identity` succeeds.

## Step 2: Create a rollback point

Back up every existing target configuration before writing. Do not print file
contents.

On macOS or Linux:

```bash
RUN_ID="$(date +%Y%m%d-%H%M%S)"
BACKUP_DIR="$HOME/.aws/.24g-mcp-setup-backups/$RUN_ID"
mkdir -p "$BACKUP_DIR"
: > "$BACKUP_DIR/manifest.tsv"

save_mcp_config() {
  source_path="$1"
  backup_name="$2"
  if [ -f "$source_path" ]; then
    cp -p "$source_path" "$BACKUP_DIR/$backup_name"
    printf '%s\t%s\n' "$backup_name" "$source_path" >> "$BACKUP_DIR/manifest.tsv"
  else
    printf 'ABSENT\t%s\n' "$source_path" >> "$BACKUP_DIR/manifest.tsv"
  fi
}
```

Call `save_mcp_config` once for each target path. Use distinct backup names,
such as `cursor-mcp.json`, `claude.json`, `gemini-settings.json`,
`kiro-mcp.json`, and `codex-config.toml`.

On Windows, create
`%USERPROFILE%\.aws\.24g-mcp-setup-backups\<timestamp>` and use `Copy-Item`
for each existing target file. Record absent paths in a manifest so rollback
can remove files created by this run.

Tell the user the rollback path. Do not delete it until they confirm the setup.

To restore on macOS or Linux, use the manifest from this run:

```bash
while IFS="$(printf '\t')" read -r saved original; do
  if [ "$saved" = "ABSENT" ]; then
    rm -f "$original"
  else
    mkdir -p "$(dirname "$original")"
    cp -p "$BACKUP_DIR/$saved" "$original"
  fi
done < "$BACKUP_DIR/manifest.tsv"
```

Show the manifest and ask before running this command. On Windows, apply the
same rule with `Copy-Item`: restore recorded files and remove only paths marked
`ABSENT`. Restoring MCP configuration does not uninstall AWS CLI, `uv`, skills,
or the proxy package cache.

**Success:** Every target path is represented in the rollback manifest.

## Step 3: Run the Agent Toolkit wizard

Use the default profile selected by the user to authenticate the setup command:

```bash
aws configure agent-toolkit \
  --region us-east-1 \
  --profile <default-profile>
```

The Agent Toolkit service uses `us-east-1`; do not substitute the workload
Region here. The wizard is interactive. Let the user select agents and decide
whether to install the default AWS skills. Select AWS MCP configuration.

Record the exact MCP configuration paths printed by the command. The command
may report an entry as already configured. That does not prove its profile
allowlist is correct; inspect it in Step 4.

If the installed AWS CLI does not detect a target agent, do not invent a path.
Use the target client's documented user-level MCP path and schema, or stop and
ask the user if it is unfamiliar.

**Success:** The wizard exits zero and each detected target agent has a base
`aws-mcp` entry.

## Step 4: Add the profile allowlist

Build one space-separated string in the user-confirmed order:

```text
<default-profile> <additional-profile> <additional-profile>
```

Do not sort it after confirmation because sorting could change the default.

### JSON clients

For Cursor, Claude Code, Gemini CLI, and Kiro, add or update only the `env`
object inside `mcpServers.aws-mcp`:

```json
{
  "mcpServers": {
    "aws-mcp": {
      "command": "uvx",
      "args": [
        "mcp-proxy-for-aws@latest",
        "https://aws-mcp.us-east-1.api.aws/mcp",
        "--metadata",
        "INSTALL_SOURCE=aws-cli"
      ],
      "env": {
        "AWS_MCP_PROXY_PROFILES": "readonly-24g app-24g production-24g"
      }
    }
  }
}
```

The snippet is illustrative. Preserve the exact `command`, `args`, `timeout`,
`transport`, package name, metadata, and every unrelated setting generated on
the user's machine. Merge with an existing `env` object rather than replacing
it.

Do not use `AWS_PROFILE`: it selects only one profile and does not enable the
proxy's per-call profile switching.

### Codex TOML

Codex uses `mcp_servers`, not JSON's `mcpServers`. Preserve the generated
command and arguments, then add or update the environment table:

```toml
[mcp_servers.aws-mcp]
command = "uvx"
args = [
  "mcp-proxy-for-aws@latest",
  "https://aws-mcp.us-east-1.api.aws/mcp",
  "--metadata",
  "INSTALL_SOURCE=aws-cli",
]

[mcp_servers.aws-mcp.env]
AWS_MCP_PROXY_PROFILES = "readonly-24g app-24g production-24g"
```

If the existing Codex file expresses `env` inline, update that map instead of
adding a conflicting table.

### Existing `--profile` arguments

If an existing `aws-mcp` entry already has `--profile` arguments, show the
user the profile names from that argument and the requested allowlist.
`AWS_MCP_PROXY_PROFILES` takes precedence, but leaving two different lists is
confusing. Ask whether to remove the stale `--profile` segment or stop. Do not
silently reconcile them.

**Success:** Every target `aws-mcp` entry contains the exact same confirmed
`AWS_MCP_PROXY_PROFILES` value.

## Updating the allowlist later

If the optional `gsso` helper is installed, it can update all detected
user-level agent configurations together:

```bash
gsso mcp add
gsso mcp remove
gsso mcp default
```

With no arguments, `gsso mcp add` edits the whole allowlist: it lists every
local profile with the allowed ones already checked, so unchecking one removes
it. `gsso mcp remove` shows the same menu limited to the profiles you currently
allow. Both use a dependency-free checkbox menu in a capable terminal: Up/Down
moves, Space toggles, `/` starts a profile-name search, `d` marks the default,
and Enter saves exactly what is checked. While searching, type to filter, press
Enter to finish the search, or Esc to clear it. Limited terminals fall back to
a numbered multi-select (`d3` marks item 3 as default). They also accept one or
more exact profile names, in which case `add` is purely additive:

```bash
gsso mcp add app-24g production-24g
gsso mcp remove production-24g
gsso mcp default readonly-24g
```

The proxy still uses the first `AWS_MCP_PROXY_PROFILES` name as the default.
`gsso mcp default` only reorders the existing allowlist. If detected agents
already disagree, `gsso` truncates to the intersection (the profiles every
agent already allows), keeps the shortest list's order, and writes that shared
list everywhere. If they share no profiles, the current list is treated as
empty and `gsso mcp add PROFILE` becomes the new shared allowlist. Restart the
affected agents after any change.

Without `gsso`, update the allowlist manually.

When access changes:

1. Run the 24G SSO setup workflow again if a local profile must be added.
2. Confirm the new ordered allowlist with the user.
3. Back up every affected MCP configuration.
4. Replace only `AWS_MCP_PROXY_PROFILES` in each `aws-mcp` entry.
5. Remove revoked profiles from the allowlist even if they still exist in
   `~/.aws/config`.
6. Restart every affected agent and repeat Step 6.

To use another account later, the user should not add it casually from inside
an agent session. They should update the explicit allowlist through this
workflow.

## Troubleshooting

### The Agent Toolkit does not accept several `--profile` values

Expected. The global AWS CLI `--profile` option accepts one profile for the
setup command. Multi-profile configuration belongs to the MCP proxy and is
added in Step 4.

### The MCP starts with the wrong account

The first name in `AWS_MCP_PROXY_PROFILES` is the default. Reorder the
confirmed list, update every target config, and restart the agents.

### `ProfileNotFound`

The allowlist contains a name that does not exactly match
`aws configure list-profiles`. Correct the allowlist; do not create a guessed
profile.

### `The SSO session associated with this profile has expired`

Run:

```bash
aws sso login --sso-session 24g
```

Then verify the affected profile with `aws sts get-caller-identity --profile
<name>` and restart the agent.

### `JSON-RPC error: -32602: Invalid request parameters("")`

The proxy commonly fell back to a missing or unusable default profile. Confirm
that `AWS_MCP_PROXY_PROFILES` exists in the server process environment, that
its first profile is valid, and that the agent was restarted after editing.

### An agent can see a profile that was not approved

Check for a stale `--profile` argument and for an inherited
`AWS_MCP_PROXY_PROFILES` in the parent shell. The MCP entry's environment
value should be the confirmed allowlist and takes precedence. Restart the
client after correction.

### The wizard says `already configured`

Continue to Step 4. `already configured` means the base `aws-mcp` entry exists;
it does not verify the multi-profile allowlist.

### The wizard does not detect an installed agent

Confirm the agent's configuration directory exists and that it is a supported
version. Use the client's documented user-level configuration only if its
schema is known. Otherwise stop rather than writing to a guessed path.

### A JSON or TOML file fails validation

Restore that file from the rollback point before retrying. Do not run the
agent against a partially repaired configuration.
